# Brace Map 踩坑记录

这份文档记录开发过程中遇到的所有「看起来该work但不work」的问题。每一条都写清楚：**现象、我当时的判断、真相、怎么确认的、教训**。

写它的目的不是复述历史，是让下次遇到同类问题能少走弯路。**尤其是那些我判断错了好几次的地方。**

---

## 一、阅读视图：flex 子项的 float 是废的

**现象**

给代码块写 `float: right`，图确实跑到右边了，但文字不绕，从下一行重新开始。

**我当时的判断**

以为是宽度没设对，或者 `width` 和 `float` 冲突。

**真相**

Obsidian 阅读视图的 `.markdown-preview-sizer` 是 `display: flex; flex-direction: column`，代码块容器是它的**直接子项**。CSS 规范明确规定：**flex 容器的直接子项，`float` 不产生浮动效果**——计算值还是 `right`，布局上被当成 `none`。

图看着在右边，只是因为 `width: 400px` 加上主题给正文块的 `margin: 0 auto` 把它推过去了。

**怎么确认的**

headless 里复刻同样的 flex 结构，量出来：

```
sizer display = flex
flex 子项计算后 float = right     ← 计算值还是 right
浮动盒 x = 16 ~ 836               ← 宽度还是满宽 820，没缩
段落各行宽度 = [816, 352]          ← 第一行 816，完全没绕
```

**教训**

`float` 的计算值正常，**不代表它生效**。遇到「float 写了没效果」，第一件事是查父级的 `display` 是不是 flex / grid。

主题的图片浮动能用，是因为 `float` 加在 `<img>` 上，而 `<img>` 外面还有一层 `<p>`，本身不是 flex 子项。

## 二、给块加 margin 不够，必须同时给 max-width

**现象**

给后续块加了 `margin-right`，行宽一点没变。

**真相**

不少主题给正文块写死了 `width`。只加 `margin-right` 时，盒子被挤出容器外，**内容区宽度不变**，文字还是那么宽。

**解法**

`margin-right` 和 `max-width` 一起做，才同时兼容自动宽和定宽。

**教训**

「加间距」和「缩内容」是两件事。`box-sizing: content-box` 下，padding / margin 不改变内容区宽度。

---

## 三、canvas 量文字，离屏时字号会兜成 14px

**现象**

折行宽度算错，文字溢出。

**真相**

用 canvas 的 `measureText` 量文字宽度时，如果宿主节点还没插进可见文档，`getComputedStyle` 拿不到 `font-size`，代码里 `parseFloat('') || 14` 就兜成了 **14px**，而实际字号是 19.95px。

**解法**

双级探针（先问宿主，拿不到问 `document.body`），并且 `ensureFont()` **独立于校准结果无条件**挂到可见节点上校验字号。

**教训**

`|| 默认值` 这种写法会把「拿不到」伪装成「拿到了一个小值」，报错变成静默偏差。**测量类代码里，拿不到就应该显式失败，不该兜底。**

## 四、Obsidian 内置的 MathJax 出不了矢量

**现象**

公式渲染不出来，或者出来是位图不是矢量。

**真相**

从 `obsidian.asar` 里解出来的事实：`tex2svg` 出现 **0 次**，`CHTML` 出现 **307 次**，配置里写着 `renderer: "CHTML"`。

**Obsidian 只带了 CHTML 输出，根本没有 SVG 输出器。**

**解法**

自己打包 `vendor/tex-svg.js`（2MB），随插件走。

**教训**

「Obsidian 有 MathJax」不等于「Obsidian 的 MathJax 能干我要的事」。**包装了的库要查它实际带了哪些模块。**

---

## 五、MathJax 在模块作用域里加载，startup 不跑

**现象**

把 `tex-svg.js` 用 CommonJS 的方式加载，只建出一个壳对象，`startup` 从来不执行。

**真相**

模块工厂里执行时，MathJax 的初始化流程依赖顶层的 `window` 环境和脚本执行时序。走 `require` 这条路，它只是定义了对象，不会自己启动。

**解法**

用 `app.vault.adapter.getResourcePath()` 拿到真实路径，动态插入 `<script>` 标签在**顶层**加载，加载前后保存恢复 `window.MathJax`。

**教训**

**第三方库的「加载方式」会影响「初始化行为」**，不是所有 UMD 包都能塞进模块系统里用。

## 六、CM6 的真实 DOM 结构，跟我从 CSS 推出来的不一样

**现象**

编辑模式的浮动逻辑一直静默放弃，日志里全是 `lpf.wait`，五轮重试后 `giveup`，一句话不留。

**我当时的判断**

以为是 flex 的问题（照搬阅读视图的结论），或者 `float` 在 CM6 里无效。

**真相**

我照着 `app.css` 推的层级是 `.cm-content > .cm-line > .cm-embed-block`，**实际是 `.cm-content > .cm-embed-block`，中间没有 `.cm-line` 那一层**。

日志里的祖先链：

```
div.block-language-brace.bm-floated.bm-float-right
  div.cm-preview-code-block.cm-embed-block...cm-lang-brace
    div.cm-content.cm-lineWrapping        ← 直接就是 content
      div.cm-contentContainer
        div.cm-sizer
          div.cm-scroller
            div.cm-editor
```

诊断字段：`hasEmbed: true, hasContent: true, hasLine: false`。

**教训**

**样式表能告诉我类名和属性，不能告诉我运行时 DOM 长什么样。**手上有安装包，就该直接读运行时结构，或者加一行诊断打印祖先链，而不是从 CSS 反推。

这一条我错得最久，从「CM6 里 float 无效」这个错误前提出发，后面十几轮都在给这个前提打补丁。

## 七、CM6 的高度账本 —— 最深的那个坑

**现象**

编辑模式开着浮动，**点击第 18 行，光标出现在第 14 行**，光标还能飘到行与行之间的空隙里。

**真相**

CM6 用**累加行高**来估算文档总高和每行的位置。你点鼠标时，它拿纵坐标去翻这本账，算出「大概第几行」。

而 **block widget 会被单独记一条高度**。widget 一旦浮动（脱离流，实际占 0），账上还是原来的高度：

```
CM6 账上的文档总高   7504.13
DOM 实际高度         7334.34
差                   169.79    ← 正好是 widget 的高度
```

**差多少，光标就偏多少。**

**试过但没用的做法**

1. **`cm.requestMeasure()` 主动重测**：无效。诊断显示 `changed: false`，重测前后高度差恒为 0。因为 CM6 量的是 widget 自己的 rect，浮动不改变它，只是不再贡献给父容器。
2. **`height: 0` + `shape-outside`**：无效。布局引擎的浮动排除区**纵向范围就等于浮动盒自身高度**，归零之后文字彻底不绕。

   对照实验很干脆：

   ```
   浮动盒高度 0    → 文字压图 7 行
   浮动盒高度 85   → 部分绕开 3 行
   浮动盒高度 170  → 完全绕开 0 行
   ```

**为什么原生图片就没这问题**

Obsidian 把图片渲染成**行内**元素，塞在某一行文字流里。CM6 对它只有一个认知：「这一行就是正常行高」，**不单独记账**。主题给图片加 `float`，图片溢出到下面几行，CM6 的账一点没变。

**差别不在「图片特殊」，在于 CM6 要不要为它单独记一笔高度。**

**教训**

**当一个组件维护了自己的布局模型时，任何绕过它的布局改动都会被它记账记错。** 这时候要么按它的规则来，要么别动。

## 八、`contain: paint !important` 把图整张裁掉

**现象**

编辑模式里图完全不显示，但诊断显示：

```
SVG 在 DOM 里：true
实际渲染尺寸：256.0 × 128.0    ← 尺寸完全正常
```

**我当时的判断**

以为是定位错、或者被祖先 `overflow: hidden` 裁了。

**真相**

Obsidian 的 `app.css` 里有一条（从 `obsidian.asar` 里翻出来的原文）：

```css
.markdown-source-view.mod-cm6 .cm-content > [contenteditable=false] {
  contain: paint !important;
}
```

代码块 widget 正是 `.cm-content` 下 `contenteditable=false` 的子元素。**`contain: paint` 会把后代裁到自己的 padding box，而 `overflow: visible` 对它完全无效**——两套机制不是一回事。

**教训**

「元素在 DOM 里、尺寸正常、就是看不见」这个组合，八成是 `contain` / `clip-path` / `transform` 这类**不叫 overflow 的裁剪机制**。

排查顺序：`overflow` → `contain` → `clip-path` → `transform` + `overflow` → `opacity` / `visibility`。

## 九、账本「值没变就跳过」，导致永远不补

**现象**

留白写了，看不见效果，而且**一直不恢复**。

**真相**

账本里有个优化：记着自己上轮往某个元素写了什么，下轮读到同样的值就不再写。

问题在于 **CM6 会把行的 `style` 属性整个重写或清空**——它按自己的记录做 diff，发现不一致就覆盖。于是账本以为「已经写过了」，元素上其实是空的，**一次都不补**。

而且抹掉 `style` **不产生 `childList` 变化**，原来的 `MutationObserver` 根本收不到。

**教训**

**缓存「我写过什么」的前提是「别人不会改它」。** 只要有个强势的第三方会重写同一个属性，这个缓存就必须带校验，否则它就是 bug 的温床。

## 十、留白反复失效 —— 一个我没解决的问题

**现象**

**刚打开 Obsidian 时文字是避开的，等所有插件加载完之后就不避开了。**

**试过的所有办法，全部无效**

- 给后续行加 `padding-right`（headless 成立，真机不生效）
- `padding` 带 `!important`
- 同时给 `max-width` 兜底
- 「施加 → 下一帧复查 → 失败重写」三轮校验
- 1.2 秒巡检 + 插件加载完强制重算
- 每次重算记时间线、sweep 加硬保护

巡检只是让它**间歇性地闪一下又散开**，问题本身还在，反而增加了大量复杂度。

**当时的判断错在哪**

我一直在给一个不成立的方向续命。每加一层机制，看起来都更靠近答案，实际上是在**给错误的前提打补丁**。

**教训**

**加机制不等于解决问题。** 如果一个问题需要三层兜底才能勉强工作，那说明方案本身有问题，该退回去重新想，而不是继续加固。

判断标准：**这一层是为了解决「新发现的情况」，还是为了掩盖「上次没修好」？**后者就该停手。

## 十一、最终答案：一行 float

**转机**

用户说：**「关掉开关之后，编辑模式反而能混排，而且光标位置正确。」**

**真相**

`renderBraceMap` 里这段判断：

```js
const lpFloatOff = isLivePreview(host) && !lpOn;
if (!lpFloatOff) applyFloatLayout(host, cfg);
```

`isLivePreview` 判断的是 `el.closest('.cm-editor')`。而**代码块处理器拿到元素的那一刻，它可能还没插进编辑器 DOM**，`closest` 返回 null，于是判断成「不是编辑模式」，老代码照旧执行，给宿主写了 `float: right`。

**这个「误判导致的执行」，恰好是正确的做法：**

1. 宿主有了 `float: right`
2. 父级 `.cm-embed-block` 是 `position: relative`，**不是独立格式化上下文**，浮动穿透到 `.cm-content`（它是 flex item，是 BFC），后面的 `.cm-line` 真的绕排
3. `.cm-embed-block` 因为子元素浮动，**高度塌成 0**，CM6 量到 0、记账 0，两边一致，**光标不错位**

headless 验证：

```
                embed 高度   行高     文字右边界   图左边界   压图行数
contain 还在       186       51.2       803        516        0（图占整行）
只有 float          0       102.4       499        516        0
```

行高从 51.2 涨到 102.4，是「被挤窄后真的折了行」的证据。

**结果**

`src/float.js` 从 2978 行砍到 1065 行，**净删 1913 行**。整个 `remeasure.js` 删掉。编辑模式的实现只剩一行 `applyFloatLayout(host, cfg)`。

**教训**

**在我以为自己需要「模拟浮动」的地方，浏览器本来就支持浮动。**我一开始的错误前提（CM6 里 float 无效）导致后面所有工作都在错误的赛道上。

**任何时候，「算对了但表现不对」，先问一句：是不是我在跟浏览器抢它本来就能干的活？**

---

## 方法论总结

按重要性排：

1. **不要在没查证的前提下给结论。**这次「CM6 里 float 无效」直接导致十几轮的弯路，而真相只是结构没看对。

2. **静态文件和运行时是两回事。**从 CSS 推 DOM 结构，跟从菜谱推菜的味道差不多。

3. **复刻环境不等于真实环境。**headless 里成立的东西，在真机上可能完全不成立。反过来，真机上自发出现的「正确」现象，往往指向真正的机制。

4. **「算对了但表现不对」是重构信号，不是调试信号。**

5. **加机制前先问：这是在解决新情况，还是在掩盖上次没修好？**

6. **用户观察到的时间点信息，常常比日志更有价值。**「刚打开是对的、加载完就不对」这一句，比几十行日志更快地缩小了范围。

7. **该停的时候要停。**用户说「不要陷入循环」的时候，我已经该停了。

## 十二、一个层数上限，把整个功能静默关掉了

**现象**

`valign`（图的垂直基准）在真机上**一次都没生效**，而同一份代码在 headless 复刻里跑得好好的。

**真相**

```js
const CLIMB_LIMIT = 4;
```

判断「宿主在不在编辑区里」用的是 `climbTo(host, 'cm-editor')`，它靠 `classList.contains` 一层层往上爬，上限 4 层。而真实链路是：

```
host → .cm-embed-block → .cm-content → .cm-contentContainer → .cm-sizer → .cm-scroller → .cm-editor
   1          2              3                  4               5            6              7
```

**第 4 层只摸到 `.cm-contentContainer`，`.cm-editor` 还在上面三层，永远够不着。**

于是每次都走「不在编辑模式」分支直接返回，排了补拍也每次都失败，连一条日志都不留。而 `applyFloatLayout` 不做这个检查，所以浮动一直是好的——两个功能共用一套结构假设，只有一个被这个上限卡死了。

**修法**

判 `.cm-content`（第 3 层），或者干脆用 `closest`（走选择器引擎，没有层数上限）。

**教训**

**手写爬升函数时，层数上限是一个静默的开关。**它不会报错，只会让判断恒为 false，而 false 分支往往写着「优雅地什么都不做」。这类 bug 在 headless 里永远不会暴露，因为它复刻的结构往往比真机浅。

判「某元素在某个容器里」应该用 `closest`，那是浏览器给的能力，不要自己数层。

## 十三、诊断在量之前记账，留下一条骗人的记录

**现象**

诊断文件里一直显示：

```
valign：middle（float right）
valign 量到的行高 lineH：31.50（记录）
valign 量到的图高 imgH：0.00（记录）
```

「记录」两个字说明 `host.__bmValignInfo` 存在，读的是 `applyValignLayout` 写下的值。于是我去查「为什么图高是 0」，查了好几轮。

**真相**

原代码的顺序是：

```js
const info = { ... };
host.__bmValignInfo = info;          // 先挂账
const embed = host.parentElement;
if (!embed || host.isConnected === false) return 0;   // 在这里返回
info.imgH = round2(elHeight(host));  // 根本没执行
```

**账挂上了，量还没做就返回了。**留下一条「记录存在、字段全 0」的残影，诊断把它当成真实测量值读了出来。

而同一个页面里另一张同配置的图「现场量」出来是 169.79，两个数字对不上，才暴露了这一点。

**修法**

先量完、再记账。中途返回就不该留下任何可被读成「已测量」的东西。

**教训**

**一个对象只要被挂到全局可达的位置，它的「存在」就会被后续代码当作「已完成」。**诊断尤其容易中招，因为它分不清「有记录」和「记录可信」。

顺序上，把「发布」放在「算完」之后，是所有状态机的通用规则。

## 十四、编辑模式一行就够，阅读模式要重写留白链

**同样的功能，两条路的难度差一个量级。**

**编辑模式**：宿主真 `float: right`，浏览器负责两件事——把图放右边、把绕排区算出来。我要做的只是补一个 `margin-top`，**浏览器自己会把这个偏移算进绕排区**。一行代码。

**阅读模式**：宿主在 flex 容器里（CSS 规范规定 flex 子项的 float 无效），没有浮动可用。只能手工拆成两步：`position: absolute` 把图挪过去，再给后面每个块加 `margin` 让文字让开。**位置和留白是两个独立计算的量，靠代码对齐。**

于是有了这条链：

```js
collectWrapTargets(block.nextElementSibling, record.height)  // 图盖住下面几个块
applyWrapMargins(targets, side, span)                        // 给这几个块加横向留白
```

**链条里藏着一个隐式假设：图从「第一个兄弟的顶边」开始。**图一旦上下偏移，这个假设就破了：

- 图下移 50px，仍被算成覆盖了整个第一块 → 下面多让出一块空白
- 图上移 100px，实际盖住了第一块上半部分，甚至盖到上面的块 → 留白漏掉那一截

**修法是给累加起点加一个偏移参数**，而不是重写整条链：

```js
let acc = startOffset;      // 原始顶边到图顶的距离，负值表示图上移
if (acc >= startOffset + h) break;
```

**教训**

**在自己模拟浏览器行为的地方，任何一个量的改变都要问「有没有别的量依赖它」。**真的 `float` 只有一个量（浮动位置），浏览器把它和绕排绑在一起；手工模拟时它们是两套独立计算，改一个就必须同步另一个。

反过来，**能用浏览器原生的地方就别自己模拟**。编辑模式那一行 float 之所以简单，不是因为我聪明，是因为我把活交给了布局引擎。

## 十五、诊断把「历史记录」和「现场测量」摆在一起，把我带偏了十几轮

**现象**

诊断文件里，两张配置完全相同的图：

```
图 A：lineH 31.50（记录）｜imgH 0.00（记录）
图 B：lineH 31.50（现场量）｜imgH 169.79（现场量）
```

我一直在问「为什么同一张图一个量到 0、一个量到 169.79」。

**真相**

诊断代码里有一句：

```js
const vHow = vi ? '记录' : '现场量';
```

有 `__bmValignInfo` 就读历史值，没有才现场量。**这些字明明就在括号里，我却一直把它们当成同一时刻的两种测量法在对比。**

一个来自过去某次调用，一个来自当下。两个不同时刻、不同代码路径的数并排放在一起，对不上是必然的。

**教训**

**诊断输出里，只要一个值不是「现在量的」，就必须让它在视觉上和现场值区分开。**用「记录」两个字太弱了，应该带时间戳或者序号，让人一眼看出它是什么时候的。

更根本的：**排查时先问「这两个数是不是同一个量」，再问「为什么不一样」。**

## 十六、「测量失败」和「结果就是 0」共用一个出口，把已经做对的东西抹掉

**这是 `valign` 一直看起来不生效的真正原因。**

**现象**

功能写了、算了、写了样式，用户每次看到的都是「没变化」。

**轨迹里的四行：**

```
#32  render    → write      hHost=150.89  yTitle=73.00  off=-57.25  wrote=1
#34  observer  → same       hHost=150.89  off=-57.25  wrote=1
#42  observer  → offset=0   hHost=0.00    yTitle=NaN   off=0.00    wrote=0
#56  retry     → !inEditor  hHost=169.79  yTitle=91.90
```

先正常写了 `-57.25px`，复查也没问题。**然后在一次回调里量到图高 0（图那一刻不在文档里），算出偏移 0，于是把刚写好的 margin-top 还原掉了。**

**根因**

代码里这两种情况走同一个出口：

- 「这张图不该偏移」（`bottom` 档）→ 偏移 0 → 把旧值还原成 0
- 「这次没量着」（图不在文档里 / 还没渲染）→ 也得到偏移 0 → **同样把旧值还原成 0**

第一种是对的，第二种是灾难：**一次暂时的测量失败，抹掉了一个正确的结果，而且不会自动恢复。**

**修法**

量到「没准备好」时直接返回，**不写、不撤、不覆盖记录**。两道门：

1. 图高为 0 或根节点数为 0
2. `middle` 档量不到标题中心

**教训**

**「算出来是 0」和「没法算」必须走不同分支。**只要它们汇到同一个 `return 0`，就会出现「正确结果被错误地撤销」。

推而广之：任何「幂等重算」的逻辑，都要先回答「这次算出来的值可信吗」，而不是直接拿它去覆盖上一次的结果。

## 十七、反馈循环很慢时，改变测量方式比继续猜更有效

**这一条是方法论，不是技术细节。**

`valign` 在阅读模式上烧了十几轮。每一轮的流程都一样：我读代码 → 猜一个原因 → 改一处 → 用户重载 Obsidian → 跑诊断 → 把文件发我。**一轮十几分钟，而且猜错就是白花。**

**为什么一直猜错**

因为我拿不到运行时。每一次都只能看到「最终状态」，看不到中间过程。所以同一个现象可以有好几种解释，我每次挑一种去验证，挑错就归零。

**转折点**

不再猜，改成**把每次调用完整记录下来**：从哪个入口进、在哪个分支返回、十几个中间量各是什么。一份轨迹拿在手上，四个调用一串，答案自己就出来了——它写对了、复查通过了、然后被自己撤了。**这件事不靠推理，靠数据。**

**教训**

**当反馈循环很慢（重启、手动操作、人工取数）时，不要做「一次验证一个假设」的循环。**应该花一次成本，把过程完整码下来，再一次性读完。

判断标准：如果需要三轮以上才能定位，那从第二轮开始就该改成「加全部观测」而不是「加一个假设」。

更极端的做法：让程序把它的判断直接画在界面上（比如在它认为的对齐位置画个标记）。**人眼对比一张图，比读一百行日志快。**
